7. Validation & Verification

1. Обозначения

Выявим способы проверки того, что платформа дистанционного обучения с прокторингом соответствует заявленным требованиям, корректно работает в штатных сценариях и сохраняет приемлемое качество при отказах внешних зависимостей.

Для этого применимы следующие методы:

  • Test (T) - тестирование системы или отдельной функции по заранее заданному сценарию
  • Analysis (A) - анализ логов, метрик, отчётов, результатов тестирования: нагрузочного, fault-injection или статистического
  • Inspection (I) - инспекция требований, настроек, журналов, структуры данных, конфигураций, версий моделей, датасетов или артефактов без обязательного выполнения пользовательского сценария
  • Demo (D) - демонстрация end-to-end сценария для заказчика, преподавателя, администратора учебного подразделения

3. Тест-кейсы

TC-01 - Успешный вход через SSO и назначение роли

Цель

Подтвердить, что пользователь проходит вход через SSO, платформа получает токен, создаёт локальную сессию и вычисляет права пользователя на основе локальной RBAC-модели с использованием атрибутов SSO

Предусловия

  1. SSO доступен
  2. В SSO существует студент student01
  3. В SSO существует проктор proctor01
  4. Платформа настроена на получение атрибутов пользователя из SSO

Шаги

  1. Открыть платформу
  2. Нажать “Войти”
  3. Убедиться, что пользователь перенаправлен в SSO
  4. Выполнить вход под student01
  5. Проверить, что открыт личный кабинет стдуента
  6. Проверить, что студент не видит функции преподавателя, проктора и администратора
  7. Повторить вход под proctor01
  8. Проверить, что проктор видит панель наблюдения, но не видит настройки администратора

Ожидаемые результаты

  1. Пользователь перенаправляется в SSO
  2. После успешного входа платформа создаёт локальную сессию
  3. Роль назначается корректно
  4. Пользователь видит только функции, соответствующие его роли

Постусловия

В логах есть запись успешной авторизации и назначения роли

TC-02 - Отказ SSO и работа локальной сессии

Цель

Подтвердить, что при недоступности SSO система не создаёт новые сессии, но при этом сохраняет ограниченный доступ пользователям с действующей локальной сессией

Предусловия

  1. У пользователя student01 есть активная локальная сессия
  2. Смоделирован отказ SSO
  3. Есть второе устройство без локальной сессии

Шаги

  1. Открыть платформу под student01 с активной локальной сессией
  2. Обновить страницу платформы
  3. Проверить доступность функций, не требующих повторной аутентификации
  4. Открыть платформу на втором устройстве без локальной сессии
  5. Попытаться выполнить вход через SSO
  6. Проверить логи

Ожидаемые результаты

  1. Пользователь с действующей локальной сессией сохраняет ограниченный доступ
  2. Новый пользователь без локальной сессии не может войти
  3. Новая сессия не создаётся
  4. В логах зафиксирована недоступность SSO

Постусловия

Создан протокол проверки отказа SSO

TC-03 - Успешный старт экзамена с прокторингом

Цель

Подтвердить, что авторизованный студент с доступной попыткой может начать экзамен. При этом создаётся экзаменационная сессия, загружается задание, запускается таймер и инициализируется античит

Предусловия

  1. Студент авторизован
  2. Экзамен доступен по расписанию
  3. Попытки не исчерпаны
  4. Камера, микрофон и экран доступны и разрешены
  5. LMS, SFU и античит доступны

Шаги

  1. Открыть страницу экзамена
  2. Разрешить доступ к камере, микрофону и экрану
  3. Нажать “Начать экзамен”
  4. Проверить создание экзаменационной сессии
  5. Проверить загрзуку заданий
  6. Проверить запуск таймера
  7. Проверить инициализацию античита

Ожидаемые результаты

  1. Экзамен запускается только после всех проверок допуска
  2. Создаётся уникальный exam_session_id
  3. Студент получил задания
  4. Таймер запущен
  5. Античит инициализирован и привязан к сессии

Постусловия

Экзамен находится в статусе “в процессе”

TC-04 - Недоступность LMS при старте экзамена

Цель

Проверить, что при проблемах с LMS (Moodle) система не создаёт некорректную попытку и не запускает экзамен без заданий, используя retry-механизм

Предусловия

  1. Студент авторизован
  2. Экзамен доступен по расписанию
  3. LMS недоступна (таймаут или ошибка 5xx)

Шаги

  1. Открыть страницу экзамена
  2. Нажать “Начать экзамен”
  3. Проверить поведение интерфейса
  4. Проверить логи интеграции с LMS (наличие повторных вызовов с backoff)
  5. Восстановить доступность LMS
  6. Повторить старт экзамена

Ожидаемые результаты

  1. При недоступной LMS экзамен без заданий не начинается
  2. Пользователь получает понятное сообщение о временной проблеме
  3. Система выполняет не менее 3 повторных попыток с увеличивающейся задержкой
  4. После восстановления LMS экзамен может быть запущен без потери попытки

Постусловия

Причина сбоя сохранена в журнале экзаменационной сессии

TC-05 - Потеря интернет-соединения во время экзамена

Цель

Подтвердить, что при потере соединения экзамен продолжается в оффлайн-режиме, ответы сохраняются локально (не позднее 2 секунд) и синхронизируются после восстановления (не позднее 120 секунд для разрыва до 10 минут)

Предусловия

  1. Экзамен запущен
  2. Студент ввёл часть ответов
  3. Моделируется недоступность сети на клиенте

Шаги

  1. Ответить на несколько вопросов
  2. Прервать интернет-соединение на 5 минут
  3. Продолжить ввод ответов (не менее 3 изменений)
  4. Проверить отображение статуса “offline” (оффлайн)
  5. Восстановить интернет-соединение
  6. Дождаться синхронизации (замерить время)
  7. Завершить экзамен
  8. Проверить сохранённые ответы на сервере

Ожидаемые результаты

  1. Экзамен не завершается автоматически при разрыве
  2. Ответы сохраняются локально, задержка сохранения <= 2 секунды
  3. После восстановления синхронизация завершается <= 120 секунд
  4. Нет конфликтов версий или потери ответов (потеря <= 1% сессий)
  5. В логах есть время начала и окончания оффлайн-периода

Постусловия

Сессия завершена, ответы сохранены на сервере

TC-06 - Недоступность SFU и локальная запись

Цель

Проверить, что при недоступности SFU система переключается на локальную запись за <= 3 секунд, сохраняя возможность постпроверки экзамена

Предусловия

  1. Экзамен запущен, видеопоток активен
  2. Камера, микрофон и экран доступны
  3. Моделируется отказ SFU (сервер недоступен)

Шаги

  1. Начать экзамен, убедиться в наличии видеопотока у проктора
  2. Смоделировать отказ SFU
  3. Замерить время до появления статуса “локальная запись”
  4. Проверить инициализацию локальной записи на клиенте
  5. Восстановить SFU
  6. Дождаться загрузки локальной записи
  7. Проверить хеш и доступность записи

Ожидаемые результаты

  1. Экзамен продолжается без онлайн-видеопотока
  2. Переключение на локальную запись выполняется за <= 3 секунды
  3. Проктор видит статус “поток недоступен - локальная запись”
  4. После восстановления связи запись подгружается
  5. Сессия получает статус “требует пост-проверки”

Постусловия

Локальная запись загружена и связана с exam_session_id

TC-07 - Завершение экзамена и сохранение артефактов

Цель

Подтвердить, что после завершения экзамена ответы, камера, микрофон, экран и события античита сохраняются как единый связанный набор данных с успешной фиксацией не менее чем в 99.5% сессий

Предусловия

  1. Экзамен запущен
  2. Во время экзамена есть не менее одного события прокторинга
  3. Медиозапись ведётся штатно

Шаги

  1. Выполнить задания
  2. Завершить экзамен
  3. Дождаться подтверждения сохранения результата
  4. Открыть карточку экзаменационной сессии
  5. Проверить наличие ответов
  6. Проверить наличие видео, аудио и записи экрана
  7. Проверить наличие журнала событий
  8. Проверить привязку всех данных к одному exam_session_id

Ожидаемые результаты

  1. Ответы сохранены
  2. Медиа-файлы сохранены, для них доступен хеш
  3. Журнал событий сохранён
  4. Все артефакты связаны с одной экзаменационной попыткой
  5. Проверка целостности при загрузке успешна

Постусловия

Сессия доступна для просмотра преподавателем, проктором или администратором

TC-08 - Регистрация подозрительного события античитом

Цель

Проверить, что античит создаёт инцидент при подозрительном событии и уведомление проктора доставляется не позднее 5 секунд (p95) при штатной нагрузке

Предусловия

  1. Экзамен запущен
  2. Проктор подключен и открыл панель наблюдения
  3. Античит включён

Шаги

  1. Смоделировать подозрительное событие (уход из кадра или переключение вкладки)
  2. Замерить время от события до появления уведомления у проктора
  3. Открыть панель проктора
  4. Найти созданный инцидент
  5. Проверить тип события, время, session_id и ссылки на артефакты

Ожидаемые результаты

  1. Инцидент создаётся автоматически
  2. Уведомление проктору доставлено за <= 5 секунд (p95)
  3. В карточке инцидента есть тип события, время фиксации и привязка к сессии
  4. К инциденту приложены ссылки на артефакты

Постусловия

Инцидент находится в статусе “ожидает решения проктора”

TC-09 - Решение проктора по инциденту и фиксация аудита

Цель

Подтвердить, что проктор фиксирует решение по инциденту, а система сохраняет его в неизменяемом виде с записью автора и времени

Предусловия

  1. Существует зарегистрированный инцидент
  2. Проктор авторизован
  3. Проктор имеет доступ к фрагменту записи и логам события

Шаги

  1. Открыть карточку инцидента
  2. Просмотреть связанные артефакты
  3. Выбрать решение “подтверждено” или “ложное срабатывание”
  4. Добавить комментарий
  5. Сохранить решение
  6. Проверить журнал решений
  7. Подтвердить получение уведомления студентом (при нарушении)

Ожидаемые результаты

  1. Решение сохранено с идентификатором проктора и временем
  2. Комментарий сохранён
  3. Решение привязано к исходному инциденту
  4. При подтверждении нарушения студент получает уведомление
  5. Аудит-запись неизменяема

Постусловия

Инцидент больше не в статусе “ожидает решения”

TC-10 - Массовые события античита и приоритетная очередь

Цель

Проверить, что при большой нагрузке (до 1000 событий/мин) события агрегируются, задержка доставки <= 5 секунд (p95), а потери событий не более 0.2%

Предусловия

  1. Запущено несколько экзаменационных сессий (>= 10)
  2. Античит включён
  3. Есть инструмент генерации тестовых событий

Шаги

  1. Сгенерировать 1000 событий/мин в течение 5 минут (разные сессии, разная критичность)
  2. Открыть панель проктора
  3. Проверить задержку от генерации до отображения в UI (p95)
  4. Проверить группировку повторяющихся событий для одной сессии
  5. Проверить порядок сортировки по уровню риска (высокий -> выше)
  6. Сверить количество доставленных событий с сгенерированными

Ожидаемые результаты

  1. Повторяющиеся однотипные события агрегированы
  2. Задержка p95 <= 5 секунд, при всплеске до 3000/мин <= 12 секунд
  3. Потери событий не превышают 0.2%
  4. События высокого риска отображаются выше
  5. Очередь инцидентов упорядочена по приоритету

Постусловия

Создан отчёт по обработке массовых событий

TC-11 - Настройка политики прокторинга и версионирование

Цель

Подтвердить, что администратор учебного подразделения изменяет параметры античита, система версионирует политику и применяет новую версию только к новым экзаменам (не влияя на уже созданные)

Предусловия

  1. Администратор учебного подразделения авторизован
  2. Существует политика прокторинга v1
  3. Есть экзамен exam-01, созданный до изменения политики

Шаги

  1. Открыть настройки прокторинга
  2. Изменить “максимальное количество переключений вкладок” с 3 на 1
  3. Сохранить настройки
  4. Проверить создание версии политики v2
  5. Создать экзамен exam-02 после изменения политики
  6. Проверить политику экзамена exam-01 (должна быть v1)
  7. Проверить политику экзамена exam-02 (должна быть v2)
  8. Проверить лог доставки параметров в античит (время <= 60 секунд)

Ожидаемые результаты

  1. Некорректные параметры блокируются валидацией
  2. Новая политика сохранена как v2
  3. exam-01 продолжает использовать v1
  4. exam-02 использует v2
  5. В журнале аудита есть автор, время и изменённые параметры

Постусловия

Политика v2 активна только для новых экзаменационных сессий

TC-12 - Подача апелляции студентом

Цель

Проверить, что студент может подать апелляцию только по завершённой и оценённой сессии в пределах установленного окна, с обязательным указанием причины

Предусловия

  1. Есть завершённый и оценённый экзамен студента (статус “оценён”)
  2. Окно подачи апелляции открыто (например, 3 дня после публикации)
  3. Есть экзамен в статусе “in progress” и “on evaluation”

Шаги

  1. Открыть завершённый и оценённый экзамен
  2. Нажать “Подать апелляцию”
  3. Попытаться отправить форму без причины
  4. Заполнить причину апелляции (обязательное поле)
  5. Отправить форму и замерить время подтверждения
  6. Открыть экзамен в статусе “on evaluation”
  7. Проверить доступность кнопки апелляции для него

Ожидаемые результаты

  1. Без причины апелляция не отправляется
  2. При указании причины создаётся запись апелляции
  3. Время подтверждения регистрации <= 3 секунд (p95)
  4. Для экзамена “on evaluation” апелляция недоступна
  5. Преподаватель получает уведомление о новой апелляции

Постусловия

Апелляция доступна для рассмотрения

TC-13 - Валидация ML-модели перед релизом

Цель

Подтвердить, что ML-модель прокторинга перед выпуском проверяется на размеченной выборке, а её качество (f1-score) >= 0.8

Предусловия

  1. Есть размеченная выборка экзаменационных сессий (1000-2000 сессий)
  2. Выборка отражает реальное поведение (разные типы нарушений, освещение, качество камеры)
  3. Зафиксирована новая версия ML-модели и датасета

Шаги

  1. Запустить новую модель на тестовой выборке
  2. Сравнить предсказания модели с ручной разметкой
  3. Рассчитать precision, recall
  4. Рассчитать F1-score
  5. Проверить долю ложных срабатываний (R-05)
  6. Проверить долю пропущенных нарушений (R-06)
  7. Сравнить результаты с предыдущей стабильной версией модели

Ожидаемые результаты

  1. F1-score >= 0.8
  2. Нет резкого ухудшения precision или recall (>5%) относительно стабильной версии
  3. Версия модели, датасета и порогов зафиксирована в отчёте
  4. Если качество ниже порога, модель не выпускается в эксплуатацию

Постусловия

Сформирован отчёт валидации ML-модели

TC-14 - Шифрование видеопотоков и проверка целостности данных

Цель

Проверить, что все медиапотоки и данные передаются по TLS, хранятся в зашифрованном виде, а система обнаруживает попытки подмены клиентского приложения

Предусловия

  1. Включена передача медиапотоков
  2. Настроено шифрование соединений (TLS 1.2+)
  3. Есть тестовый клиент с возможностью модификации

Шаги

  1. Запустить экзамен
  2. Перехватить трафик между клиентом и backend (проверить TLS)
  3. Перехватить трафик между клиентом и SFU
  4. Проверить параметры хранения медиафайлов (шифрование на диске)
  5. Смоделировать попытку подмены клиентского приложения (изменение бинарного файла)
  6. Проверить реакцию системы (отказ в подключении или инцидент безопасности)

Ожидаемые результаты

  1. Все соединения используют TLS, сертификаты валидны
  2. Доля сессий без шифрования < 0.01%
  3. Данные и медиапотоки не передаются в открытом виде
  4. Система обнаруживает подмену клиента и блокирует сессию или фиксирует инцидент
  5. Результаты проверки отражены в отчёте безопасности

Постусловия

Сформирован протокол проверки безопасности данных
