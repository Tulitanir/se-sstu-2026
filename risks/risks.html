1. Шкала оценки рисков

Для оценки рисков используется качественно-количественная шкала по двум параметрам: вероятность наступления риска (Risk Probability) и степень влияния на систему (Influence Degree). Каждый параметр оценивается по шкале от 1 до 3.

Вероятность наступления риска (Risk Probability - R)

  1. Низкая - 1 балл - Событие маловероятно и возникает только при редких сбоях, ошибках конфигурации или нестандартных условиях эксплуатации
  2. Средняя - 2 балл - Событие может возникать периодически: при высокой нагрузке, сбоях внешних интеграций, проблемах сети или ошибках пользователей
  3. Высокая - 3 балла - Событие ожидаемо в реальной эксплуатации и может регулярно возникать у части пользователей или при массовом проведении экзаменов

Степень влияния на систему (Influence Degree- I)

  1. Низкая - 1 балл Влияет на отдельного пользователя или отдельную некритичную функцию, не приводит к потере результатов экзамена или нарушению регламентов
  2. Средняя - 2 балла Влияет на группу пользователей, вызывает задержки, обращения в поддержку, спорные ситуации или временное снижение качества прокторинга
  3. Высокая - 3 балла Может привести к срыву экзамена, потере результатов, невозможности подтвердить честность аттестации, нарушению требований безопасности или правовым последствиям

Расчёт приоритета

Приоритет риска рассчитывается как произведение I и R

Интерпретация приоритета риска:

  • I = 1 (1x1), I = 2 (1x2, 2x1) - низкий риск;
  • I = 3 (3x1, 1x3), I = 4 (2x2) - средний риск;
  • I = 6 (2x3, 3x2) - высокий риск;
  • I = 9 (3x3) - критический риск.

3. Меры реагирования по каждому риску

R-01 - Пользователь не может войти в систему или получает неверную роль

1. Предотвращение

  1. Проверять валидность токена SSO на серверной стороне, а не только на клиенте.
  2. Назначать роли только на основании доверенных атрибутов, полученных из SSO.
  3. Использовать RBAC-проверки для всех защищённых операций.
  4. Не создавать новые локальные сессии, если SSO недоступен.

2. Обнаружение

  1. Логировать ошибки входа, истечения токенов и отказов SSO.
  2. Отслеживать рост ошибок авторизации за короткий период.
  3. Уведомлять администратора при превышении порога ошибок входа.

3. Реагирование и восстановление

  1. Для пользователей с действующей локальной сессией сохранять ограниченный доступ.
  2. При восстановлении SSO повторно синхронизировать атрибуты и роли.
  3. При спорном доступе временно блокировать расширенные права до проверки.

4. Fallback / режим деградации

  1. Разрешить работу только пользователям с ранее созданной и действующей локальной сессией.
  2. Запретить создание новых сессий и новых учётных записей до восстановления SSO.

5. Пост-инцидент

  1. Проанализировать логи SSO и платформы.
  2. Уточнить правила сопоставления ролей и атрибутов.
  3. При необходимости обновить тесты авторизации.

R-02 - Экзаменационные задания не загружаются из Moodle

1. Предотвращение

  1. Проверять доступность LMS (Moodle) до начала экзаменационного окна.
  2. Предварительно кэшировать структуру экзамена и метаданные попытки.
  3. Использовать повторные запросы с увеличивающейся задержкой.
  4. Валидировать формат данных, полученных из LMS (Moodle).

2. Обнаружение

  1. Мониторинг времени ответа Moodle.
  2. Фиксировать ошибки загрузки заданий по каждому экзамену.
  3. Отображать администратору список экзаменов с проблемной синхронизацией.

3. Реагирование и восстановление

  1. Перезапустить загрузку заданий без создания дублирующей попытки.
  2. Перенести старт экзамена или открыть резервное окно.
  3. Сохранить причину сбоя в журнале экзаменационной сессии.

4. Fallback / режим деградации

  1. Если экзамен был предварительно подготовлен, использовать локально сохранённые метаданные.
  2. Если задания недоступны полностью, запретить старт экзамена и уведомить администратора.

5. Пост-инцидент

  1. Сопоставить сбои LMS (Moodle) с временем массового запуска экзаменов.
  2. Обновить регламент предварительной проверки интеграции.
  3. Добавить тестовые сценарии на некорректные ответы Moodle.

R-03 - Потеря интернет-соединения во время экзамена

1. Предотвращение

  1. Автоматически сохранять ответы локально после каждого изменения.
  2. Хранить локальное состояние таймера и текущей попытки.
  3. Использовать очередь несинхронизированных действий.
  4. Не завершать экзамен автоматически при кратковременном разрыве соединения.

2. Обнаружение

  1. Отслеживать статус соединения клиента с сервером.
  2. Показывать студенту статус “offline-режим”.
  3. Логировать время начала и окончания разрыва связи.

3. Реагирование и восстановление

  1. После восстановления сети автоматически синхронизировать ответы и события.
  2. Проверять конфликты версий данных.
  3. Подтверждать студенту успешную отправку несохранённых данных.
  4. При невозможности синхронизации передавать сессию на ручную проверку.

4. Fallback / режим деградации

  1. Разрешить продолжение экзамена в offline-режиме.
  2. Ограничить доступ только текущей экзаменационной сессией.
  3. Запретить действия, требующие подтверждения сервера, кроме сохранения текущего экзамена.

5. Пост-инцидент

  1. Сформировать отчёт по длительности offline-периода.
  2. Проверить полноту синхронизации ответов и логов.
  3. При необходимости передать сессию преподавателю на дополнительную проверку.

R-04 - Проктор не видит видеопоток в реальном времени

1. Предотвращение

  1. Использовать health-check медиасервиса (SFU) перед стартом массового экзамена.
  2. Масштабировать SFU под ожидаемое количество одновременных видеосессий.
  3. Настроить лимиты и мониторинг задержек медиапотоков.
  4. Проверять соединение клиента с SFU при старте экзамена.

2. Обнаружение

  1. Фиксировать потерю видеопотока.
  2. Показывать проктору статус “поток недоступен / локальная запись”.
  3. Отслеживать количество сессий, перешедших в локальную запись.

3. Реагирование и восстановление

  1. Автоматически включать локальную запись камеры, микрофона и экрана.
  2. Вычислять хеш локальной записи для проверки целостности.
  3. Загружать запись после восстановления соединения.
  4. Переводить экзамен в режим последующей оффлайн-проверки.

4. Fallback / режим деградации

  1. Продолжить экзамен без онлайн-видеопотока, но с обязательной локальной записью.
  2. Пометить сессию как требующую проверки после завершения.

5. Пост-инцидент

  1. Проверить журналы SFU и клиента.
  2. Сравнить длительность недоступности с SLA.
  3. Пересмотреть расчёт мощности медиасервера перед следующими экзаменами.

R-05 - Ложные срабатывания античита

1. Предотвращение

  1. Подбирать чувствительность античита под тип экзамена.
  2. Не принимать автоматическое событие как окончательное нарушение без проверки.
  3. Использовать несколько признаков нарушения, а не один сигнал.
  4. Проводить регулярную оценку качества античита по precision, recall и F1-score.
  5. Перед выпуском новой ML-модели проверять её на размеченной валидационной выборке с разными условиями освещения, качества камеры и поведения студента.
  6. Версионировать модель, обучающий датасет и параметры принятия решения, чтобы при ухудшении качества можно было выполнить откат.

2. Обнаружение

  1. Отслеживать долю событий, которые проктор помечает как ложные.
  2. Сравнивать частоту срабатываний по группам, экзаменам и настройкам.
  3. Выявлять политики прокторинга, создающие слишком много ложных событий.
  4. Мониторить деградацию ML-модели: рост доли ложных срабатываний, снижение precision, recall и F1-score.
  5. Проводить выборочную ручную разметку сессий и сравнивать решения модели с решениями прокторов.

3. Реагирование и восстановление

  1. Дать проктору возможность изменить статус события на “ложное”.
  2. Исключать ложные события из итоговой оценки нарушения.
  3. Передавать спорные случаи на рассмотрение преподавателю.
  4. Корректировать параметры античита после анализа серии ложных срабатываний.
  5. При подозрении на некачественную работу модели переводить её события в режим обязательной ручной проверки.
  6. Откатывать ML-модель на последнюю стабильную версию, если новая версия резко увеличила количество ложных срабатываний.

4. Fallback / режим деградации

  1. При высокой доле ложных срабатываний переводить сессии в режим ручной проверки.
  2. Временно снижать чувствительность наиболее шумных правил.
  3. До исправления ML-модели использовать более консервативный режим: автоматическое событие считается поводом для проверки, но не окончательным нарушением.

5. Пост-инцидент

  1. Использовать подтверждённые ложные срабатывания для улучшения правил античита, обучающей выборки и качества ML-модели.
  2. Обновить документацию по интерпретации событий для прокторов.
  3. Проверить, не связаны ли ложные срабатывания с конкретным типом оборудования или действия.
  4. Провести переобучение или калибровку модели на пополненной и сбалансированной выборке.

R-06 - Реальное нарушение не зафиксировано системой

1. Предотвращение

  1. Записывать экзамен даже при отсутствии активного проктора.
  2. Настраивать пороги античита в зависимости от строгости экзамена.
  3. Проводить выборочную постпроверку сессий.
  4. Перед внедрением новой ML-модели проверять recall по ключевым типам нарушений, чтобы модель не пропускала критичные события.
  5. Контролировать качество обучающего датасета: баланс классов, разные устройства, освещение, качество камеры и типовые сценарии поведения студентов.

2. Обнаружение

  1. Анализировать необычные паттерны: частые потери фокуса, отсутствие лица, шумы, подозрительные паузы.
  2. Сравнивать события античита с видеозаписью и логами действий.
  3. Выявлять сессии с низким качеством наблюдения.
  4. Отслеживать случаи, когда нарушение найдено вручную, но не было зафиксировано ML-моделью.
  5. Периодически оценивать recall и F1-score на контрольной размеченной выборке.

3. Реагирование и восстановление

  1. Помечать сомнительные сессии как “требует проверки”.
  2. Давать преподавателю доступ к артефактам экзамена.
  3. При подтверждении нарушения фиксировать решение с указанием времени, причины и доказательств.
  4. Использовать результаты разбора для настройки античита.
  5. Добавлять пропущенные нарушения в датасет ошибок для последующего дообучения или корректировки правил.
  6. При падении recall временно ужесточать правила или откатывать ML-модель до стабильной версии.

4. Fallback / режим деградации

  1. Если событие не было зафиксировано автоматически, разрешить ручное создание инцидента проктором или преподавателем.
  2. При недостаточности доказательств использовать процедуру апелляции.
  3. При подозрении на слабую модель увеличивать долю ручной постэкзаменационной проверки.

5. Пост-инцидент

  1. Разобрать причину пропуска нарушения: недостаток обучающих данных, слабая разметка, неверный порог модели или плохое качество видеопотока.
  2. Добавить новый сценарий в тестирование античита.
  3. Пересмотреть правила наблюдения и инструкции для прокторов.
  4. Провести калибровку порогов и регрессионный тест ML-модели перед повторным выпуском.

R-07 - Неверная политика прокторинга применяется к экзамену

1. Предотвращение

  1. Валидировать параметры перед сохранением.
  2. Запрещать конфликтующие настройки.
  3. Версионировать политики прокторинга.
  4. Применять новую версию политики только к новым экзаменационным сессиям.

2. Обнаружение

  1. Логировать каждое изменение политики: кто изменил, когда, старое и новое значение.
  2. Отслеживать ошибки доставки настроек в античит.
  3. Показывать администратору актуальную версию политики для каждого экзамена.

3. Реагирование и восстановление

  1. При ошибке доставки отправлять параметры античиту через очередь.
  2. Не менять правила для уже начатых экзаменов.
  3. Передавать спорные сессии на ручную проверку.

4. Fallback / режим деградации

  1. Если античит недоступен, сохранять изменения политики в очереди.
  2. До подтверждения применения использовать последнюю стабильную версию политики.

5. Пост-инцидент

  1. Проверить журнал изменений политики.
  2. Выяснить, какие экзамены были затронуты.
  3. При необходимости провести пересмотр спорных результатов.

R-08 - Потеря или повреждение экзаменационных артефактов

1. Предотвращение

  1. Использовать уникальный идентификатор экзаменационной сессии.
  2. Вычислять хеши медиафайлов.
  3. Использовать репликацию и резервное копирование в объектном хранилище.

2. Обнаружение

  1. Проверять успешность загрузки каждого артефакта.
  2. Сравнивать хеш файла до и после загрузки.
  3. Отслеживать сессии с неполным набором данных.

3. Реагирование и восстановление

  1. Повторно загружать повреждённые или неполные файлы.
  2. Если видео отсутствует, рассматривать апелляцию по доступным логам и ответам.
  3. Помечать сессию как требующую ручной проверки.
  4. Фиксировать техническую причину потери артефакта.

4. Fallback / режим деградации

  1. При недоступности облачного хранилища временно сохранять артефакты в локальной очереди.
  2. При неполном наборе данных использовать доступные артефакты и явно отмечать ограничения проверки.

5. Пост-инцидент

  1. Провести сверку сессий с неполными артефактами.
  2. Проверить настройки хранения, репликации и удаления.
  3. Обновить механизм контроля целостности данных.
