# 3.2. Системные требования (SR-SYS)

### SR-SYS-1 (Сценарий 1 - Переход в SSO)
> При инициировании пользователем входа в систему, система должна перенаправлять пользователя в систему аутентификации (SSO).

**Верификаиция:** функциональный тест (инициирование входа => пользователь перенаправлен в SSO)

### SR-SYS-2 (Сценарий 1 - Успешный вход в систему)
> При успешной аутентификации пользователя в SSO система должна принимать и обрабатывать токен доступа, возвращённый SSO.

**Верификация:** функциональный тест (SSO возвращает валидный токен => система обрабатывает токен и продолжает процесс авторизации).

### SR-SYS-3 (Сценарий 1 - Безуспешный вход в систему)
> При безуспешной аутентификации пользователя в SSO система не должна создавать пользовательскую сессию, уведомив пользователя об ошибке.

**Верификация:** функциональный тест (SSO возвращает ошибку аутентификации => пользователь не авторизован => отображено сообщение об ошибке)

### SR-SYS-4 (Сценарий 1 - Назначение ролей)
> При успешной аутентификации пользователя система идентифицирует пользователя через SSO и определяет права доступа согласно локальной моделью ролей (RBAC).

**Верификация:** функциональный тест
(получен токен SSO -> пользователь сопоставлен с локальной моделью ролей -> доступны только разрешённые функции)

### SR-SYS-5 (Сценарий 1 - Истечение токена: без повторной аутентификации со стороны пользователя)
> При обнаружении истечения срока действия токена доступа пользователя система должна инициировать процесс получения нового токена через SSO и, при успешном получении нового токена, продолжать текущую пользовательскую сессию без повторной аутентификации и пересоздания сессии.

**Верификация:**  функциональный тест (истёкший токен => система выполняет запрос к SSO => получает новый токен => пользователь сохраняет свою сессию без повторного входа)

### SR-SYS-6 (Сценарий 1 - Истечение токена: с необходимостью повторной аутенфикации со стороны пользователя)
> При невозможности автоматического получения нового токена через SSO система должна прекращать выполнение защищённых операций (за исключением уже начатой экзаменационной сессии - см. SR-SYS-21) и требовать от пользователя повторного входа.

**Верификация:** функциональный тест (новый токен не получен => блокировка защищённых операций (кроме активного экзамена) =>
редирект на SSO)

### SR-SYS-7 (Сценарий 1 - Заблокированный пользователь)
> Если пользователь имеет статус "blocked", система должна запрещать выполнение операций от имени данного пользователя, в том числе и вход в систему.

**Верификация:** функциональный тест (пользователь с валидными SSO-данными, но статусом "blocked" => сессия не создается, доступа к системе нет => сообщение о блокировке)

### SR-SYS-8 (Сценарий 1 - Недоступность SSO)
> При недоступности SSO система должна обеспечивать ограниченный доступ для пользователей с ранее установленной и действующей локальной сессией. Для других - доступ не предоставлять.

#### В ограничённом режиме 
1. Разрешены:
- продолжение активного экзамена и действий в его рамках (ввести ответ, завершить экзамен);
- просмотр уже загруженных материалов;
2. Запрещены:
- запуск новых экзаменов;
- изменение профиля;
- создание новых пользовательских сессий.

**Верификация:** функциональный тест:
SSO недоступен:
- пользователь без локальной сессии => доступ запрещён
- пользователь с валидной локальной сессией => ограниченный доступ предоставлен

### SR-SYS-9 (Сценарий 2 - Допуск к старту экзамена)
> Система должна разрешать запуск экзамена только авторизованному студенту в назначенное время.

**Верификация:** функциональный тест (авторизованный студент + наступило время экзамена => запуск разрешён).

### SR-SYS-10 (Сценарий 2 - Согласие на прохождение экзамена)
> При переходе на вкладку с экзаменом система должна запросить у пользователя согласие на условия прохождения экзамена.

**Верификация:** функциональный тест (студент перешел на вкладку с экзаменом => система запросила согласие на условия проведения экзамена).

### SR-SYS-11 (Сценарий 2 - Запрос доступа к камере и микрофону)
> Перед началом экзамена система должна инициировать запрос разрешений на доступ к камере, микрофону и экрану пользователя, необходимых для проведения прокторинга.

**Верификация:** функциональный тест (пользователь открывает окно со страницей экзамегна => появляется запрос доступа к камере, микрофону и экрану => пользователь разрешает доступ => становится активной кнопка "Начать экзамен").

### SR-SYS-12 (Сценарий 2 - Проверка и блокировка старта)
> Система должна разрешать начало экзамена только при согласии с условиями наличии доступа к камере, микрофону и экрану, и должна блокировать запуск экзамена при отсутствии хотя бы одного из требуемых разрешений или недоступности устройств.

**Верификация:** функциональный тест (доступ к камере/микрофону отсутсвтует или согласие отсутсвует => старт заблокирован).

### SR-SYS-13 (Сценарий 2 - Создание экзаменационной сессии)
> После успешного прохождения всех проверок допуска к экзамену (SR-SYS-9-12) система должна создавать уникальную экзаменационную сессию, связанную с конкретным пользователем.

**Верификация:** функциональный тест (пользователь прошёл все проверки допуска => выполнено "Начать экзамен" => создана экзаменационная сессия).

### SR-SYS-14 (Сценарий 2 - Подключение видеопотока)
> После создания экзаменационной сессии система должна устанавливать соединение с медиа-сервисом и передавать медиапотоки, связанные с экзаменационной сессией пользователя.

**Верификация:** интеграционный тест (создана экзаменационна сессия => медиапотоки успешно передаются в медиа-сервис).

### SR-SYS-15 (Сценарий 2 - Включение античита и анализатор медиапотокоа)
> После создания экзаменационной сессии система должна инициализировать античит и анализатор медиапотоков, передавая идентификатор экзаменационной сессии и параметры наблюдения, для последующего анализа пользовательской активности в ходе экзамена.

**Верификация:** интеграционный тест (создана экзаменационная сессия => античит и анализатор медиапотоков получают идентификатор сессии и параметры конфигурации => инициализация выполнена).

### SR-SYS-16 (Сценарий 2 - Выдача вопросов и запуск экзамена)
> После успешного завершения всех этапов инициализации экзаменационной сессии система должна предоставлять доступ к экзаменационных заданиям, загруженным из внешней LMS.

**Верификация:** функциональный тест (экзамен начат => отображаются экзаменационные вопросы).

### SR-SYS-17 (Сценарий 2 - Фиксация записи камеры, микрофона и экрана)
> Во время активной экзаменационной сессии система должна обеспечивать захват и сохранение медиапотоков (видеопоток с камеры, аудиопоток с микрофона и поток экрана пользователя) с привязкой к идентификатору экзаменационной сессии при штатной работе системы.

**Верификация:** функциональный тест (экзамен заупщен => создаются записи всех предусмотренных источников).

### SR-SYS-18 (Сценарий 2 - Сохранение результатов вместе с записями)
> После завершения экзаменационной сессии система должна сохранять результаты экзамена, медиа (камера, микрофон, экран) и журнал событий прокторинга как связанный набор данных, ассоциированный с идентификатором экзаменационной сессии.

**Верификация:** функциональный тест (экзамен завершен => сохранены ответы, видео и аудио, события прокторинга и связаны с уникальным индентификатором экзаменнационной сессии).

### SR-SYS-19 (Сценарий 2 - Потеря интернет-соединения)
> При потере интернет-соединения во время активной экзаменационной сессии система должна переводить экзамен в оффлайн-режим, обеспечивать локальное сохранение вводимых ответов и состояния таймера, а также сохранять возможность продолжения выполнения экзамена без прерывания пользовательской сессии.

**Верификация:** функциональный тест (разрыв соединения => система не завершает экзамен, сохраняет ответы локально и имеет состояние "offline").

### SR-SYS-20 (Сценарий 2 - Локальная запись в оффлайн-режиме)
> При переходе в оффлайн-режим система должна выполнять записи медиапотоков (камера, микрофон, экран) локально до последующей синхронизации. Локальные медиафайлы должны сохраняться в зашифрованном виде и удаляться после успешной синхронизации.

**Верификация:** интеграционный тест (оффлайн-режим => запись продолжается локально с буферизацией медиа-файлов до момента возвращения в онлайн-режим => онлайн-режим => синхронизация => удаление локальных медиа).

### SR-SYS-21 (Сценарий 2 - Недоступность SSO)
> Если недоступность SSO возникает во время активной экзаменационной сессии, система должна обеспечивать непрерывность выполнения экзамена, включая ввод и сохранение ответов, без прерывания сессии пользователя, при условии действующей локальной экзаменационной сессии.

**Верификация:** функциональный тест:
- пользователь начал экзамен
- SSO становится недоступен
- Система не завершает экзамен, продолжает отображать задания, сохраняет ответы, пользователь может завершить экзамен

---

### SR-SYS-22 (Сценарий 3 - Регистрация подозрительного события)
> При обнаружении подозрительного события античитом или анализа медиопотоков система должна создавать запись события, содержащую тип события, время фиксации, идентификатор экзаменационной сессии и ссылку на связанные артефакты (медиа и логи). Далее приведены классы подозрительных событий:

**Подозрительные события античита:**
1. Переключение вкладок и окон
2. Потеря фокуса окна
3. Сторонняя попытка захвата экрана
4. Обнаружена виртуальная машина
5. Обнаружен отладчик
6. Аномально быстрый ввод
7. Долгое бездействие

**Подозрительные события анализа медиапотоков:**
1. Несколько лиц в кадре
2. Отсутсвие лица в кадре
3. Постронние голоса или шум
4. Частое отведение взгляда
5. Лишние предметы в кадре       

**Верификация:** функциональный тест (произвести моделирование подозрительного события => создается запись о событии с указанием типа, времени фиксации, идентификатора экзаменационной сессии и ссылкой на связанные артефакты).

### SR-SYS-23 (Сценарий 3 - Уведомление проктора)
> После регистрации события система должна отправлять проктору уведомления, содержащее идентификатор экзаменационной сессии, тип события и ссылку на связанные артефакты (медиа и логи).

**Верификация:** функциональный тест (создаётся запись о событии => проктор получает уведомление).

### SR-SYS-24 (Сценарий 3 - Доступ проктора к фрагменту записи)
> Для зарегистрированного события система должна предоставлять проктору доступ к связанному медиофрагменту, включающему видеопоток с камеры и синхронизированные аудио- и экранные данные

**Верификация:** функциональный тест (получено уведомление об инциленте => проктор открывает зарегистрированное событие => система отображает видеофрагмент и временную шкалу события)

### SR-SYS-25 (Сценарий 3 - Фиксация решения проктора)
> Система должна позволять проктору фиксировать решение по зарегистрированному событию с указанием типа решения, комментария и подтверждающих артефактов. Решение должно быть привязано к событию и сохраняться в системе с записью идентификатора проктора и времени решения.

**Типы решений:**
1. "warning" - предупреждение
2. "violation confirmed" - подтвержденное нарушение
3. "violation rejected" - ложное нарушение/срабатывание
4. "exam terminated" - прервать экзамен
5. "review required" - требуется доп. проверка

**Верификация:** функциональный тест (существует запись события => проктор принимает решение => система сохраняет тип решения, время решения, идентификатор проктора).

### SR-SYS-26-a (Сценарий 3 - Подтверждённое нарушение со статусом "violation confirmed" или "warning")
> При публикации нарушения со статусом "violation confirmed" или "warning" система должна отправить студенту предупреждение с комментарием проктора и временем фиксации.

**Верификация:** функциональный тест (проктор подтверждает нарушение со статусом "violation confirmed" => студент получает уведомление).

### SR-SYS-26-b (Сценарий 3 - Подтверждённое нарушение со статусом "exam terminated")
> При публикации нарушения со статусом "exam terminated" система должна прервать выполнение экзамена и отправить студенту причину заершения с комментарием проктора.

**Верификация:** функциональный тест (проктор подтверждает нарушение со статусом "exam terminated" => экзамен завершается => студент получает уведомление).

### SR-SYS-26-с (Сценарий 3 - Событие со статусом "review required")
> При наличии событий со статусом "review required" завершенный экзамен должен получать статус "check required" вместо "on evaluation".

**Верификация:** функциональный тест (проктор назначает событию статус "review required" => завершенный экзамен получает статус "check required").

### SR-SYS-27 (Сценарий 3 - Массовые события)
> При массовом поступлении событий в рамках экзаменационной сессии (> 100 событий/(мин*сессия)) система должна агрегировать события и ранжировать их путем оценки риска (низкий, средний, высокий, критический)

**Верификация:** функциональный тест (загрузка множество событий => система ранжирует события по значимости с присвоением уровня риска).

### SR-SYS-28 (Сценарий 3 - Режимы деградации при недоступности проктора)
> Если проктор недоступен в момент экзамена или после его завершения, система должна обеспечивать возможность принятия решения по результатам экзамена на основе сохранённых артефактов (ответы студента, медиозаписи и журналы событий). При этом экзамен по завершении получает статус "check required"

**Верификация:** функциональный тест (проктор отсутствует => система сохраняет все артефакты => студент завершает экзамен => экзамен завершается со статусом "check required").

---

### SR-SYS-29 (Сценарий 4 - Доступ администратора учебного подразделения к настройкам прокторинга)
> Система должна предоставлять доступ к разделу "Настройки прокторинга" только пользователям с ролью администратора учебного подразделения.

**Верификация:** функциональный тест (пользователь с ролью "Администратор учебного подразделения" имеет доступ к настройкам. Пользователь с иной ролью такого доступа не имеет).

### SR-SYS-30 (Сценарий 4 - Настройка параметров прокторинга)
> Система должна позволять авторизованному администратор учебного подразделения организации изменять набор параметров прокторинга (античит и анализатор медиапотоков), используемых для обнаружения подозрительных действий в рамках экзаменационных сессий. Изменения должны фиксироваться и доставляться на сервер прокторинга с подтверждением применения.

**Верификация:** функциональный тест (администратор изменяет параметр => система валидирует значение, сохраняет конфигурацию и отправляет на сервер прокторинга => сервер прокторинга получает параметр и использует в новых сессиях => сервер прокторинга уведомляет основной backend о применении настроек).

### SR-SYS-31 (Сценарий 4 - Настройка срока хранения записей)
> Система должна позволять администратор учебного подразделения задавать срок хранения экзаменационных данных (включая видеозаписи, аудиозаписи, экранные записи, ответы студентов и журналы событий) в ограниченном диапазоне (например, 30-365 дней)

**Верификация:** функциональный тест (администратор задаёт срок хранения => система сохраняет настройку).

### SR-SYS-32 (Сценарий 4 - Политика хранения данных)
> Система должна автоматически обеспечивать удаление экзаменационных данных по истечении установленного срока хранения. При этом удаление данных запрещено до момента закртытия активной апелляции (если та была инициирована на данный экзамен). Срок хранения автоматически продлевается на период рассмотрения активной апелляции

**Верификация:** функциональный тест: 
1. истек срок хранения записей для экзамена без активной апелляции => данные становятся недоступны, выполняется удаление.
2. истек срок хранения записей для экзамена с активной апелляцией => срок хранения продлен на период апелляции

### SR-SYS-33 (Сценарий 4 - Сохранение и применение новых политик)
> Система должна обеспечивать версионирование политик прокторинга и применять актуальную версию политики только к экзаменационным сессиям, созданным после момента её публикации, сохраняя неизменность ранее назначенных политик для уже созданных экзаменов.

**Верификация:** функциональный тест:
1. создаётся политика v1 => создаётся экзамен A => экзамен A использует v1
2. изменяется политика => создаётся v2 => создаётся экзамен B => экзамен B использует v2
3. Проверка:
- экзамен A всегда использует v1
- экзамен B всегда использует v2
- изменение v2 не влияет на экзамен A

---

### SR-SYS-34 (Сценарий 5 - Сроки рассмотрения апелляции)
> Система должна позволять администратор учебного подразделения задавать срок рассмотрения апелляции для экзаменов 

**Верификация:** функциональный тест (администратор задаёт срок рассмотрения => система сохраняет настройку).

### SR-SYS-35 (Сценарий 5 - Доступность подачи апелляции)
> Система должна предоставлять студенту возможность подать апелляцию только по экзамену, находящемуся в статусе "completed", и только в пределах установленного администратором временного окна после публикации результата.

**Верификация:** функциональный тест:
1. экзамен в статусе "in progress" или "on evaluation" => апелляция недоступна
2. экзамен оценён => апелляция доступна
3. истекло время подачи апелляции => апелляция недоступна

### SR-SYS-36 (Сценарий 5 - Обязательность указания причины)
> При подаче апелляции система должна создавать уникальную запись апелляции, связанную с результатом экзаменационной сессии, фиксировать обязательную причину обращения, и устанавливать начальный статус "registered".

**Верификация:** функциональный тест:
1. попытка отправить апелляцию без причины => отклоняется системой
2. попытка отправить с причиной => апелляция создаётся, причина фиксируется в неизменном виде, записи апелляции назначается уникальный индентификатор и статус "registered"
