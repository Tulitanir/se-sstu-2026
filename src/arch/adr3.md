## ADR-3. Выбор технологии кеширования для обеспечения отказоустойчивости при недоступности SSO

### Контекст
Платформа онлайн-прокторинга должна сохранять доступ для студентов с активной сессией даже при отказе системы SSO. 
По требованию NFR-2, при недоступности SSO система должна обеспечивать доступ для пользователей с валидной локальной сессией в 99.9% случаев, но не должна создавать новые сессии.

Основные требования для этого сценария:
- NFR-2: доступность авторизованных операций 99.5% в месяц, сохранение доступа при отказе SSO 99.9%
- SR-SYS-8: при недоступности SSO система запрещает новые входы, но работает для пользователей с действующей сессией
- SR-SYS-21: если SSO отвалился во время экзамена, студент продолжает его без прерывания

Проблема в том, что без локального хранилища сессий система не сможет проверить, кто есть кто, когда SSO недоступен.

---

### Рассматриваемые варианты
1. Локальное хранение сессий в памяти каждого сервера приложений
2. Redis (master-replica с sentinel)
3. Хранение сессий в реляционной базе данных

---

### Решение
Используем **Redis** для хранения пользовательских сессий.

---

### Обоснование

| Критерий | Локальный кеш | Redis | Только БД |
|----------|---------------|-------|-----------|
| Сессии видны со всех серверов | Нет | Да | Да |
| Быстрая проверка сессии | Да (< 0.1 мс) | Да (< 1 мс) | Нет (5-15 мс) |
| Сессии не пропадают при рестарте | Нет | Да | Да |
| Автоочистка просроченных сессий | Да | Да | Нужна ручная настройка |
| Автоматическое восстановление при отказе | Нет | Да (sentinel) | Да |

Факторы выбора Redis:

1. Сессии видны с любого сервера. При локальном кеше сессия есть только на том сервере, где студент выполнил вход. Если запрос придет на другой сервер, он решит, что студент не авторизован. Это нарушает NFR-2.
2. При рестарте сервера локальный кеш очищается. Студенты, которые сдавали экзамен, потеряют сессию и не смогут его закончить. Redis хранит сессии на диске и восстанавливает их после перезапуска.
3. Sentinal автоматически переключит на реплику, если основной Redis упал. Система продолжит работать без ручного вмешательства.

---

### Последствия
Позитивные:
- Система не зависит от SSO при проверке уже активных сессий
- Выполняется NFR-2 (доступность 99.9% для пользователей с сессией)
- При отказе SSO во время экзамена студент ничего не замечает (SR-SYS-21)

Негативные:
- Нужно следить за сроком жизни сессии в Redis, чтобы он совпадал с токеном SSO
- Каждый запрос требует проверки сессии в Redis (сетевой вызов, но очень быстрый)
- Если весь Redis упадёт, проверять сессии станет нечем (но sentinel и реплики снижают этот риск)
